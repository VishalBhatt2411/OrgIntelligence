# ADR-0024: Record Analyze Mode Adopts the Same Directional Lane Layout as Object Mode, by Generalizing the Existing Canvas Rather Than Forking It

## Status
Accepted — extends [ADR-0023](0023-object-relationship-lane-layout.md); [ADR-0019](0019-hybrid-radial-graph-visualization.md) remains unchanged and authoritative for Field mode only, the one analyze mode still browsing a general, multi-type egocentric neighborhood.

## Context
Record analyze mode ([ADR-0021](0021-record-analysis-deferred-outside-metadata-graph.md)) has, since its own introduction, rendered through the generic radial canvas (`oiGraphCanvas`) — the same component Field mode uses. That was a reasonable default when Record mode's own dedicated layout didn't exist yet, but it leaves Record mode with two concrete, user-visible problems that ADR-0023 already solved for Object mode and never revisited for Record mode:

1. **No directional framing.** A live record's parent lookups and child records are exactly the kind of "single-type, directional relationship inventory" question ADR-0023 §Context identifies Object mode as asking — "objects that reference this one" vs. "objects this one references" — and the radial canvas's ring-by-hop-distance layout has no notion of that distinction for records either, for the identical reason ADR-0023 already gives for objects.
2. **No self-relationship handling.** `oiGraphCanvas`'s only self-relationship logic (`renderableEdges`, collapsing a same-node self-reference to a dropped zero-length edge) assumes the two endpoints resolve to the *same* node — true for an object referencing its own metadata type, never true for two distinct record nodes of the same object (e.g., one Account record's `ParentId` pointing at a different Account record). A record self-relationship therefore renders today as an ordinary, undistinguished edge between two same-typeKey cards, with none of the honest "this relates to itself" treatment ADR-0023 built for objects.

Separately, the user reported the Object-mode lane canvas's own self-relationship rendering looked broken at low zoom — traced to the canvas's zoom control applying a CSS `transform: scale()` on top of an SVG whose `width`/`height` attributes stayed at their full, unscaled size, leaving the diagram-wrapper's scrollable layout box unscaled while its visual content shrank, so the self-relationship lane (positioned below the main diagram in the same coordinate space) read as disconnected and far away. That bug is fixed in the same canvas this ADR generalizes (switching zoom to scale the SVG's own rendered width/height instead of a CSS transform) — fixing it once here, rather than once per canvas, is itself part of this decision's motivation.

## Decision
Generalize `oiRelationshipCanvas` (renamed from `oiObjectRelationshipCanvas`) to serve **both** Object and Record analyze mode, selected by a new `mode` prop, rather than forking a second, near-duplicate lane-canvas component for Record mode. Concretely:

- **A new pure presentation-transform module, `recordRelationshipView.js`**, sibling to `objectRelationshipView.js`, produces the identical `{rootObject, incomingRelationships, outgoingRelationships, selfRelationships, counts}` shape from the already-fetched Record Analysis working set (`OI_RecordHierarchyService`'s direct record-to-record `LOOKUP_TO`/`CHILD_OF` edges — no `HAS_FIELD` chain-walk needed, unlike Object mode). A counterpart record of the *same* object type as the center is classified `self` — the record-mode reading of "this relates to itself," since records are individually keyed by Id and two distinct records is what a same-typeKey pair actually means here (Object mode's self case is the same node referencing itself; Record mode's is a different node of the same type).
- **`oiRelationshipCanvas` picks the transform by `mode`** (`buildObjectRelationshipView` vs. `buildRecordRelationshipView`) and exposes mode-aware labels (lane titles, "Analyzing Object" vs. "Analyzing Record", self-card/caption text using the connector's own counterpart rather than the root, since a record self-relationship's counterpart is a genuinely different record) — the ~800 lines of org-chart geometry (card layout, trunk routing, zoom/export/maximize toolbar) are untouched and mode-agnostic; only the transform and a handful of label getters branch on `mode`.
- **The Business/System/All relationship-visibility toggle is hidden entirely in Record mode**, not offered non-functional: `OI_RecordHierarchyService`'s fragment carries no originating field API name for a record edge, so there is no data to classify System vs. Business by. `filterByVisibility` bypasses filtering for Record mode so every fetched relationship still renders.
- **`oiRelationshipConnectorDetail` gains a `mode` prop.** Object mode's field-level breakdown ("Open Field", per-field relationship type) is omitted entirely in Record mode (no field data to show). "Open Source"/"Open Target" for a record builds a `NAVIGATION_KIND_RECORD` target (`{recordId, objectApiName}`, already parsed onto each ref via `c/recordNodeKey`) directly, client-side, and hands it to the *same* `navigateToTarget` (`c/metadataNavigation`) Object mode's Setup-page navigation already uses — no new navigation kind, no Apex call for a record open at all, since a standard record page needs no server-side URL resolution the way a Setup page does.
- **`oiGraphExplorer` gains one new branch**: `usesRelationshipCanvas` (`isObjectMode || isRecordMode`) renders `oiRelationshipCanvas` with `mode={analyzeMode}`; Field mode is untouched and still renders `oiGraphCanvas`. Record mode's "Explore From Here" (the lane canvas's only re-centering affordance, replacing the radial canvas's expand/collapse for this mode) routes through `selectAndCenterRecord` when the target nodeKey parses as a record (`c/recordNodeKey`), exactly the same branch `handleExpand` used before Record mode moved off `oiGraphCanvas` — `handleExpand` itself is simplified back to a plain metadata-only path, since Field mode (its only remaining caller) never produces a record nodeKey.
- **No Apex changes.** Every piece of this is a presentation-layer fork over data `OI_RecordHierarchyService` already returns and services `OI_GraphController`/`c/metadataNavigation` already expose — the same "presentation-layer fork over the same data and the same services" discipline ADR-0023 established for Object mode.

## Consequences
- **Positive**: Record mode gets the same directional framing, self-relationship honesty, export/zoom/maximize toolbar, and (once fixed in this same pass) correct zoom behavior that Object mode already has, without a second component to keep in sync — a bug fixed in the shared canvas (like the zoom dead-zone fix landing in this same change) benefits both modes at once.
- **Positive**: the fork is narrow and explicit — one `mode` prop, one alternate transform module, a handful of mode-aware getters and two connector-detail branches. `oiGraphExplorer`'s existing Field-mode branch, `oiGraphCanvas`, and every Field-mode filter/expand/collapse code path are entirely untouched by this change.
- **Negative**: `oiRelationshipCanvas` is no longer a single-purpose "Object relationship canvas" — a future reader must track two transform modules and a `mode` branch instead of one obviously-named component. Accepted because the alternative (a second ~800-line near-duplicate component) would have doubled the maintenance surface for layout code that is genuinely identical between the two modes, including every future bug fix to that layout — a worse outcome than one component with a documented mode seam.
- **Negative**: Record mode loses the radial canvas's expand/collapse-with-reference-counting model entirely, replaced by re-centering ("Explore From Here") — a real behavior change, not a superset. Accepted because Record mode's own data model (ADR-0021 — a fresh live query per center, no persisted graph, no reference-counted visibility) never actually supported incremental expand/collapse in the reference-counted sense GraphUI.md §13 formalizes for the metadata graph; every "expand" was already a fresh `getRecordFragment` call re-centered on the expanded node, which is exactly what re-centering is, made explicit instead of dressed up as expand.
- **Negative**: Record connectors carry no field-level detail (no `fields[]`, no System/Business classification) — a real, disclosed information gap, not silently hidden: `recordRelationshipView.js`'s own doc comment and this ADR both name it, and the UI degrades honestly (a fieldless "Related Record" label, a hidden rather than non-functional visibility toggle, no field-detail section in the connector popup) rather than fabricating detail that isn't there. A future enhancement to `OI_RecordHierarchyService` carrying the originating field's API name would unlock both without changing this ADR's shape.

## Alternatives Considered
- **Fork a second `oiRecordRelationshipCanvas` component, mirroring `oiObjectRelationshipCanvas` structurally** — rejected: the two would share the entire org-chart geometry engine (card layout, trunk routing, zoom math, export/maximize) byte-for-byte, differing only in the transform and a few labels. Forking would directly violate this platform's own reuse/SOLID mandate and mean every future layout bug (such as the zoom dead-zone fix landing in this same change) would need fixing twice.
- **Add a Record "mode" flag to the generic radial canvas (`oiGraphCanvas`) instead** — rejected for the same reason ADR-0023 already rejected this for Object mode: `oiGraphCanvas` is a large, generic, multi-type rendering surface, and folding a second, structurally different (single-type, directional) layout model into it risks regressing the Field-mode rendering path that still depends on it.
- **Keep Record mode on the radial canvas and only fix its self-relationship/directional gaps in place** — rejected: this would mean building the directional lane/self-relationship logic a *second* time, bespoke to the radial canvas's own data structures, rather than reusing the lane logic ADR-0023 already built and validated for exactly this kind of single-type directional question.
- **Extend `OI_RecordHierarchyService` now to carry the originating field's API name**, unlocking full field-level parity with Object mode — deferred, not rejected: this is a real, named future enhancement (see Consequences), but it is an Apex-side change with its own governor-limit and query-shape implications, and nothing in this ADR's UI-layer decision depends on it; the UI is built to degrade honestly today and improve automatically if that enhancement lands later, without another UI change.
