# ADR-0018: Denormalized `parentKey` for Object-Scoped Search Filtering, Instead of Traversal

## Status
Accepted — elaborates [ADR-0001](0001-graph-data-model-as-core-abstraction.md), [ADR-0011](0011-generic-node-edge-typing-via-domain-registry.md)

## Context
Search must support "object filtering" — e.g., scoping a Field search to only the Fields belonging to a specific Object — as a first-class capability ([SearchEngine.md §11](../SearchEngine.md#11-object-filtering--via-parentkey-never-via-traversal)). The most direct way to express "which Object does this Field belong to" today is a graph traversal: start at the Object node, walk its `HAS_FIELD` edges, and filter to those neighbors. This round's own mandate explicitly forbids exactly that — Search must not load the dependency graph, and Search and graph traversal must remain separate concerns — so the direct approach was not available, and no existing field on the Node model (GraphEngine.md §2) answered this question without one.

## Decision
Add a new, optional, generic, opaque field to the Node model: **`parentKey`** — a reference to another node's logical `nodeKey`, populated once at ingestion time by `OI_MutationGenerator` from a `parentComponentKey` the Scanner already faithfully knows for component kinds that have exactly one natural structural parent (a `CustomField`'s parent is its `CustomObject`; a `ValidationRule`'s or `RecordType`'s parent is likewise its `CustomObject`). Component kinds with no single natural parent (`ApexClass`, `Flow`) leave it blank. Search filters by `parentKey` as an ordinary indexed equality predicate — exactly as cheap and exactly as generic as filtering by `typeKey` — with zero traversal involved. Full specification: [SearchEngine.md §11](../SearchEngine.md#11-object-filtering--via-parentkey-never-via-traversal); schema: [DataModel.md §2.3](../DataModel.md#23-oi_graph_nodec); Discovery Model source field: [MetadataScanner.md §5, §15](../MetadataScanner.md#5-discovery-model).

## Consequences
- **Positive**: object-scoped filtering is answered by a single indexed `WHERE` predicate, with the same cost and the same genericity guarantee as every other Search filter — no traversal dependency, no violation of this round's separation-of-concerns mandate.
- **Positive**: `parentKey` is exactly as opaque to the Graph Engine as `secondaryKey` already is — the engine stores and indexes it without interpreting it, preserving the engine's domain-vocabulary genericity ([ADR-0011](0011-generic-node-edge-typing-via-domain-registry.md)) exactly. The engine only ever treats it as "an optional reference to another node's key," a graph-mechanics fact, not a domain-vocabulary one.
- **Positive**: this is the first concrete instance of the "promoted attribute slot" extension point GraphEngine.md §2 already flagged as future work, needing exactly one field rather than the fully general mechanism — a narrower, cheaper realization of an already-anticipated seam.
- **Negative — denormalization**: the same structural fact (Object HAS_FIELD Field) now exists in two places — an edge (used by traversal) and a field on the child node (used only by Search). This creates a theoretical drift risk if a future code change updates one path and not the other; mitigated by both being derived from the identical Scanner-observed fact in the identical Mutation Generator pass, not two independent derivations ([SearchEngine.md §29](../SearchEngine.md#29-risks)).
- **Negative**: `parentKey` is single-valued — a component with more than one natural structural parent has no representation here. No component kind designed for as of this decision needs more than one; if one ever does, this field's shape would need to change, recorded as an open question rather than solved speculatively now ([SearchEngine.md §32](../SearchEngine.md#32-open-questions)).

## Alternatives Considered
- **A live `OI_GraphTraversal` call from inside Search** — rejected outright: directly violates the explicit mandate that Search and graph traversal remain separate concerns and that Search never load the dependency graph.
- **A materialized "flattened ancestor path" attribute, recomputed on every scan** — considered, rejected as more machinery than the problem needs: every object-filtering question this platform's UI actually asks is answered by a single immediate parent, not a multi-level path; building path-flattening machinery for a need that doesn't exist yet would be exactly the kind of speculative generality `CLAUDE.md`'s Core Principles warn against.
- **Leave object filtering unimplemented until a stronger need is demonstrated** — rejected: this round's mandate explicitly requires it (§11, "Object filtering" is a named required section), and the denormalized-field approach costs one optional field, not a new subsystem — the cost of building it now is low enough that deferring it would not have been the more conservative choice.
