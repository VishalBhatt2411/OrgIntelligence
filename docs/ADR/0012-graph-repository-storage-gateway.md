# ADR-0012: GraphRepository as the Sole Storage Gateway

## Status
Accepted — elaborates [ADR-0002](0002-hybrid-custom-object-big-object-graph-persistence.md); the five-operation contract sketched below is corrected and given full treatment by [ADR-0016](0016-repository-atomic-commit-and-optimistic-concurrency.md) and [GraphRepository.md](../GraphRepository.md) — `insertVersion`/`flipCurrent` (as described in Decision, below) are merged into one atomic `commitVersion` operation, and a `getCurrentKeysByType` enumeration operation is added

## Context
ADR-0002 established a hybrid Custom Object + Big Object persistence model for the graph. It did not, at the time, specify *who* is allowed to talk to those storage backends, or how a future backend (a third or fourth storage mechanism) would be added without editing every caller that currently knows about Custom Objects and Big Objects directly. As the Graph Builder ([GraphEngine.md](../GraphEngine.md) §7) took shape, it became clear that letting the Builder (and potentially Traversal, Cache, and Serializer) each independently know how to read/write Custom Objects, Big Objects, and Platform Cache would scatter storage-format knowledge across every component instead of containing it in one place — exactly the coupling ADR-0003's layering already argues against, now recognized as needing an explicit fix at the storage boundary specifically.

## Decision
Introduce `OI_GraphRepository` as the **only** component, anywhere in the platform, permitted to issue a storage operation against node/edge data. The flow is fixed as: `Scanner → Graph Builder → Graph Repository → Storage`. The Graph Builder decides *what* should happen to a node/edge (new version, liveness touch, state transition — [GraphEngine.md](../GraphEngine.md) §7) but never *how* or *where* it's stored. The Repository itself does not branch per backend inline; it delegates to a small `OI_IGraphStorageProvider`-shaped interface, with one implementation per backend: `OI_CustomObjectStorageProvider`, `OI_BigObjectStorageProvider`, `OI_PlatformCacheStorageProvider`, and any future provider implementing the same interface ([GraphEngine.md](../GraphEngine.md) §7.1).

## Consequences
- **Positive**: adding a new storage backend (a future native Salesforce graph primitive, for instance) is a new provider class — zero changes to the Builder, Traversal, Cache, or any external caller.
- **Positive**: storage-format knowledge (field names, DML shape, Big Object index-field constraints, Platform Cache partition semantics) lives in exactly one place per backend, each isolated behind the same interface — a query-shape change in one backend can't leak into how another is used.
- **Positive**: this is what makes `OI_GraphCache`'s relationship to Platform Cache honest rather than contradictory — `OI_GraphCache` owns caching *policy* (keys, TTLs, invalidation) but issues its actual reads/writes through the Repository's `OI_PlatformCacheStorageProvider`, so "who has direct storage access" still has exactly one answer even though two facade-internal components have reasons to touch the cache backend ([GraphEngine.md](../GraphEngine.md) §7.1, §14).
- **Negative**: the Repository's own surface must be actively kept generic (five operations, per [GraphRepository.md §2](../GraphRepository.md#2-graphrepository-interface): read current versions, enumerate current keys by type, commit a version atomically, touch liveness, archive superseded) rather than growing backend-specific convenience methods per caller — this requires ongoing review discipline, flagged as a risk in [GraphEngine.md](../GraphEngine.md) §21 and [GraphRepository.md](../GraphRepository.md) §21, not a one-time design guarantee.
- **Negative**: every write now costs one extra bulk read (current-version lookup) before the actual write, since the Builder must ask the Repository for current state before deciding what to do — a real, accepted performance cost (see ADR-0014's consequences and GraphEngine.md §15/§22).
- **Positive, added by [ADR-0016](0016-repository-atomic-commit-and-optimistic-concurrency.md)**: because the Repository is also the single place write atomicity and concurrency resolution had to be solved, it turned out to be the natural, single home for both — neither concern had to be smeared across the Builder or any caller above it.

## Alternatives Considered
- **Builder talks to each backend directly (the prior implicit design)** — rejected: this is precisely the coupling this ADR exists to remove; every new backend would require touching the Builder.
- **One monolithic Repository class with `if/else` branching per backend inline** — rejected: an Open/Closed violation — adding a backend means editing the Repository's own conditional logic rather than adding an isolated implementation, and the branching only grows uglier as backends are added.
- **A separate Repository per backend, with callers choosing which one to use** — rejected: pushes the "which backend for which situation" decision back onto every caller, exactly the knowledge this ADR is trying to centralize; a single Repository dispatching to providers keeps that decision in one place.
