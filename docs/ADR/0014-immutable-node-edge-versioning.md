# ADR-0014: Immutable Node/Edge Versioning Model

## Status
Accepted — elaborates [ADR-0001](0001-graph-data-model-as-core-abstraction.md)

## Context
The original Node/Edge persistence model ([ADR-0001](0001-graph-data-model-as-core-abstraction.md), [ADR-0002](0002-hybrid-custom-object-big-object-graph-persistence.md)) upserted-by-key: a rescanned node either matched (no-op) or was updated in place, overwriting its prior content with no retained history. `GraphNode`/`GraphEdge` are now required to be immutable — never modified after creation, with updates creating a new version instead of mutating the existing object. Applied naively (every touch produces a new version, with zero exceptions), this would defeat the storage economics incremental scanning ([ADR-0009](0009-incremental-scanning-via-checksum-diffing.md)) was designed to protect: most scans touch most nodes with no actual content change, and if every touch is a new row, versioning costs exactly what incremental scanning was meant to save.

## Decision
A node/edge's *content* fields (`typeKey`, `label`, `secondaryKey`, `attributes`, `checksum`) and its lifecycle `state`, once written to a version row, are never rewritten. A real content change or a lifecycle-state transition creates a **new version row**; the row it supersedes is flipped to `isCurrent = false` and otherwise never touched again. Two fields — `lastSeenRunId` and `isCurrent` — are the sole, explicitly narrow exception: they are bookkeeping *about* a version (was it reconfirmed live, is it still current), not content, and are updated in place on the current row when an incoming observation's checksum matches what's already stored (a "liveness touch," not an update — [GraphEngine.md](../GraphEngine.md) §2, §7). This makes the Graph Builder's write path a three-way decision per observation (new node/edge, liveness touch, or new version) rather than a blind upsert, and requires `Node_Key__c`/`Edge_Key__c` to become non-unique logical identifiers (one per row-version) with a new `Node_Version_Key__c`/`Edge_Version_Key__c` taking over as the actual unique/External-ID field ([DataModel.md](../DataModel.md) §2.3/§2.4).

## Consequences
- **Positive**: no lost-update races, a genuine immutable audit trail of every real change, and a foundation — at zero additional schema cost — for future time-travel/change-narrative features ([GraphEngine.md](../GraphEngine.md) §19, §20) that a mutate-in-place model would need a bolt-on retrofit to support.
- **Positive**: the liveness-touch exception keeps the *common* case (unchanged reaffirmation, which is most nodes on most scans) exactly as cheap as before versioning was introduced — the storage/performance cost of versioning is paid only when something actually, meaningfully changed.
- **Negative — storage growth for frequently-changing entities**: a node/edge that has genuine content changes on every scan accumulates one version row per scan indefinitely unless archived. This is the single biggest cost this decision introduces, and is not hidden — it's tracked as a first-class risk ([GraphEngine.md](../GraphEngine.md) §21) with a named mitigation: the existing Big Object archival job (DataModel §7) is extended in scope to sweep aged-out non-current version rows (not only purged/soft-deleted nodes as originally scoped), reusing existing machinery rather than inventing new.
- **Negative — every write costs an extra bulk read**: the Builder must look up the current version (to compare checksums and decide which of the three paths applies) before it can issue any write — a real, non-zero cost versus a blind upsert, accepted and measured against the benefit above ([GraphEngine.md](../GraphEngine.md) §15, §22).
- **Negative — the model is not literally zero-mutation**: `isCurrent`/`lastSeenRunId` are a narrow, deliberate exception, not full purity. This is stated honestly rather than glossed over, and an alternative that removes even this exception (a `Superseded_By_Version_Key__c` self-reference instead of a mutable flag) is recorded as an open question, not foreclosed ([GraphEngine.md](../GraphEngine.md) §24).
- **Negative — every read must now scope to `Is_Current__c = true`**: any query against these objects that omits this predicate will silently surface historical rows. Mitigated by centralizing the predicate in the Selector layer rather than trusting every caller to remember it ([GraphEngine.md](../GraphEngine.md) §13, §15, §21).

## Alternatives Considered
- **Status quo — upsert-in-place, no versioning** — rejected: this is precisely what immutability was required to replace.
- **Fully-versioned with zero exceptions — every observation, including an unchanged reaffirmation, creates a new row** — rejected: defeats incremental scanning's storage economics outright, since most observations on most scans are unchanged reaffirmations; would turn a cost-saving mechanism into a cost multiplier.
- **Event-sourcing with a separate immutable event log object plus a separate mutable "current state" projection object** — considered seriously, rejected for v1 as more machinery than the problem currently needs: a single object holding both historical and current rows, distinguished by `Is_Current__c`, achieves the same guarantee with one fewer object and one fewer join for the common "get current state" read. Revisit if the version-row volume or query patterns ever justify the added structure.
- **A `Superseded_By_Version_Key__c` self-reference instead of a mutable `Is_Current__c` flag** — genuinely viable, would remove the one remaining mutation entirely; not adopted now because it changes the "find current" query shape (`WHERE Superseded_By_Version_Key__c = null` vs. `WHERE Is_Current__c = true`) for a purity gain with no identified concrete requirement driving it yet — left as an explicit open question ([GraphEngine.md](../GraphEngine.md) §24) rather than decided prematurely in either direction.
