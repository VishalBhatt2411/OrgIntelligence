# ADR-0019: Hybrid Graph-Topology, Radial-Layout Visualization — Not a Literal Tree

## Status
Accepted — elaborates [ADR-0001](0001-graph-data-model-as-core-abstraction.md)

## Context
The Visual Graph UI's primary interaction model is egocentric — a user selects one node and receives a visual, expandable relationship graph centered on it ([GraphUI.md §2](../GraphUI.md#2-user-journey)). This round's mandate explicitly requires analyzing whether a hierarchical tree, a directed graph, or a hybrid is the correct visualization strategy, rather than assuming a tree by default. The platform's own data model was already decided, well before this UI existed: [ADR-0001](0001-graph-data-model-as-core-abstraction.md) explicitly rejected a one-parent-per-relationship model because relationships are cross-type and many-to-many; [GraphEngine.md §11](../GraphEngine.md#11-expand-collapse-algorithm) explicitly designs its reference-counting visibility algorithm around nodes reachable through more than one expanded ancestor, naming this as common in real metadata graphs; [Architecture.md §7](../Architecture.md#7-dependency-engine-architecture) explicitly requires cycle detection for the Dependency Engine because Apex call graphs are genuinely cyclic. Any visualization strategy chosen here has to be consistent with a data model that already, deliberately, is not a tree.

## Decision
The underlying rendered structure is a true directed graph — cycles, shared nodes, and multiple supporting ancestors are all first-class and rendered honestly, with a shared node appearing exactly once regardless of how many currently-expanded ancestors support its visibility ([GraphUI.md §13](../GraphUI.md#13-reference-counting-visibility-model)). The *visual arrangement* defaults to a radial, egocentric layout: the currently selected/center node is anchored at the visual origin and never moves for the lifetime of one view; other nodes are placed in concentric rings by their shortest currently-known hop-distance from the center, with a light force-relaxation pass distributing nodes within a ring to reduce edge crossings ([GraphUI.md §17](../GraphUI.md#17-layout-strategy)). This gives the readability of a tree-like radiating structure for the common case (most metadata relationships have a natural "outward from here" direction) without the correctness cost of a literal tree data structure, which cannot represent a genuinely shared or multi-parent node without either duplicating it or silently hiding one of its relationships.

## Consequences
- **Positive**: no shared or cyclic relationship is ever hidden or duplicated to fit a tree shape — a direct, structural satisfaction of this round's explicit "shared nodes must not be duplicated unnecessarily" requirement.
- **Positive**: the center-node-never-moves property gives users a stable spatial mental model across many expand/collapse actions, directly serving the stated priority that clarity and discoverability outweigh decorative visualization.
- **Positive**: this independently arrives at the same pattern `CLAUDE.md`'s own stated design inspiration, Neo4j Browser, already uses by default — an egocentric, radially-arranged, topologically-honest graph — which the ADR treats as convergent validation of the choice, not a coincidence to ignore.
- **Negative**: layout logic (ring assignment, within-ring force relaxation) is more complex to build and to keep stable across expand/collapse than a naive top-down tree renderer would be — accepted because the simpler alternative is also the incorrect one for this data model.
- **Negative**: a node genuinely connected to many different rings simultaneously (reachable at different hop-distances via different paths) needs a single, well-defined ring-assignment rule (shortest known hop-distance within the currently visible set) rather than an ambiguous one — resolved explicitly in [GraphUI.md §17](../GraphUI.md#17-layout-strategy), but worth naming as an added design surface a tree renderer would never have needed to address.

## Alternatives Considered
- **Hierarchical tree** — rejected: not merely a suboptimal visualization, but the wrong data structure for this product's actual data, per the Context above. A tree cannot represent this platform's own already-decided graph model without either duplication (violating this round's mandate directly) or silent information loss.
- **Pure undirected/force-directed graph with no imposed hierarchy** — considered seriously (topologically correct, the traditional general-purpose answer): rejected as the *default* presentation because it treats every node symmetrically, undermining the stable, centered spatial model this UI's egocentric interaction design depends on, and because it degrades specifically at the hub-node failure mode ("many nodes connected to one node") this round explicitly calls out, with no layout-level help mitigating it.
- **A strict tree for the common case, with an ad hoc "shared node" special-case rendering (e.g., a dashed cross-reference line back to a canonical single position elsewhere in the tree)** — considered, rejected as more complex than the chosen hybrid while still being conceptually a tree with a patch bolted on, rather than a graph rendered honestly from the start.
