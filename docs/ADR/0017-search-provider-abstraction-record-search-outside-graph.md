# ADR-0017: Search Provider Abstraction; Record Search Kept Outside the Graph

## Status
Accepted — elaborates [ADR-0007](0007-sosl-search-behind-abstracted-service.md)

## Context
[ADR-0007](0007-sosl-search-behind-abstracted-service.md) established `OI_SearchService` as the sole seam for search, backed by SOSL, with the abstraction promise that a future backend change would be "localized to `OI_SearchService`'s internals." It did not specify a concrete mechanism for that localization, and it predates a new requirement this round: the platform must also support searching Salesforce **records** (customer business data), not only scanned metadata. Records are not, and must not become, Graph Nodes — a subscriber org's record volume is orders of magnitude larger than its metadata volume, and persisting records into the graph would directly violate the platform's "never load an entire org" posture and multiply its own storage footprint far beyond what any metadata-only design accounted for. Records also carry a fundamentally different security shape than the platform's own application-internal graph objects: [ADR-0006](0006-apex-boundary-security-model-for-app-internal-data.md)'s Custom-Permission-only gating model explicitly does not cover genuine customer business data, which requires full CRUD/FLS/sharing enforcement instead.

## Decision
Introduce `OI_ISearchProvider` as the concrete mechanism fulfilling ADR-0007's abstraction promise — a small, stable contract (`search`, `exactMatch`) that `OI_SearchService` dispatches to per search domain, directly mirroring the Storage Provider pattern [ADR-0012](0012-graph-repository-storage-gateway.md) already establishes for `OI_GraphRepository`. Two implementations exist: `OI_MetadataSearchProvider` (backed by `OI_NodeSelector` against `OI_Graph_Node__c`, unchanged backing store from ADR-0007) and `OI_RecordSearchProvider` (backed by a new `OI_RecordSelector` issuing dynamic SOSL, via `Search.query(String)`, against an admin-configured, opt-in allow-list of business sObjects — never persisted, never indexed by this platform, always queried live). Record Search is double opt-in: a master switch (`OI_Settings__mdt.Enable_Record_Search__c`, default `false`) and a per-sObject enablement flag (`OI_Record_Search_Scope__mdt.Enabled__c`, default `false` per row) — nothing is searchable until an administrator explicitly turns it on, at both levels. Ranking is centralized in `OI_SearchService`, applied uniformly to whichever provider(s) produced candidates, so a provider never needs to reimplement ranking logic. Full specification: [SearchEngine.md](../SearchEngine.md) §5, §12, §14.

## Consequences
- **Positive**: a future third search domain or a future alternate backend for an existing domain (a hosted external search service, [SearchEngine.md §26](../SearchEngine.md#26-future-external-search-providers)) is a new provider class — zero change to `OI_SearchService`'s orchestration, `OI_SearchController`, or any DTO shape.
- **Positive**: Record Search's fundamentally different security posture (full sharing/FLS vs. Custom-Permission-only) is cleanly isolated to one provider and one Selector, never leaking into the Metadata path or requiring `OI_SearchService` itself to branch on domain-specific security rules.
- **Positive**: centralizing ranking outside the providers means every current and future provider inherits consistent, tunable ranking (a shared `Search_Boost_Weight__c` mechanism, applied identically across both domains) for free.
- **Negative**: Record Search results cannot be cached in the platform's shared L1 (Org-partition Platform Cache) — caching per-user-sharing-visible business data in an org-wide cache partition would risk serving one user's visible records to another user with different sharing, a real data-leakage risk, not a theoretical one ([SearchEngine.md §20](../SearchEngine.md#20-caching)). This is an accepted, deliberate limitation, not an oversight.
- **Negative**: Record Search introduces a genuine expansion beyond the platform's stated Product Vision (`CLAUDE.md` describes the product entirely in metadata terms), a scope tension recorded honestly rather than glossed over — this ADR's recommendation, carried from [SearchEngine.md §0/§32](../SearchEngine.md#0-relationship-to-prior-documents--what-this-corrects-adds-and-challenges), is that it ship opt-in and sequenced after the metadata search experience is solid, not bundled by default just because it is specified in the same document.

## Alternatives Considered
- **Persist records as Graph Nodes, reusing all existing Search/Graph machinery uniformly** — rejected: an unbounded storage/governor-limit liability, and a category error — a record is data, not metadata, and the entire Graph Engine's genericity design (ADR-0011) is about domain *vocabulary*, not about accommodating arbitrary business-data scale.
- **A fully separate, parallel Record Search feature with its own Controller/DTO/permission model, sharing nothing with Metadata search** — rejected: would forfeit the "one unified way to search" outcome this round explicitly asked for, and would duplicate ranking/pagination/request-shaping logic that the Provider abstraction lets both domains share for free.
- **A single interleaved, federated ranked list combining both domains' results** — rejected: no principled way exists to compare relevance scores across two structurally unrelated backends without an arbitrary, indefensible weighting, or fully materializing and re-ranking both result sets, itself a bound-violating operation at real result-set sizes ([SearchEngine.md §31](../SearchEngine.md#31-alternatives-considered)). Results are domain-partitioned instead.
