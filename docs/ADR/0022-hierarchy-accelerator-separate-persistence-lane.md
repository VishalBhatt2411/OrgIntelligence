# ADR-0022: Hierarchy Accelerator as a Structurally Separate Persistence Lane, Amending ADR-0021

## Status
Proposed — amends [ADR-0021](0021-record-analysis-deferred-outside-metadata-graph.md) for this epic only. ADR-0021's live-query-only decision **stands unchanged** for ad hoc Record Analysis (Backlog RA-1/RA-2/RA-3, already built as `OI_RecordHierarchyService`/`OI_RecordHierarchyController`, wired into `oiNodeDetailPanel`/`oiGraphExplorer`).

## Context
An FRD ("Salesforce Record Multi-Hierarchy Accelerator") was evaluated against this platform's actual scope: it asks for admin-configurable, persisted, multi-hierarchy management of business records (e.g. the same Account participating in a Corporate hierarchy *and* a Territory hierarchy simultaneously), with relationship history, effective dating, and rollup metrics. ADR-0021 already assessed the adjacent question — visualizing a record's *existing* native-lookup relationships — and chose a live-query, non-persisted approach specifically because business records have a different cardinality and change-rate than metadata, and because the app's own Apex-boundary security model (ADR-0006) does not fit data with real per-record visibility rules.

ADR-0021 named a fallback it declined to build without a concrete driving need: "a structurally separate persistence lane... only if a caching/history requirement for record relationships emerges later." That need has now concretely emerged. FR-005 (a dedicated Hierarchy Relationship object, independent of native lookups), FR-017 (relationship history), and FR-018 (effective dating) cannot be built from live SOQL against native lookup fields — a Salesforce record can hold at most one native lookup value per field, so "the same Account in two independent hierarchies at once" has no live-queryable representation at all. This ADR designs that fallback.

## Decision
Build a new, structurally separate object model and service layer — the **Hierarchy Accelerator** — that persists admin-configured business-record hierarchies. It is explicitly **not** an extension of `OI_Graph_Node__c`/`OI_Graph_Edge__c`, and does not reuse ADR-0014's immutable-version-ladder pattern. Two decisions are load-bearing:

- **Security model**: `OI_Hierarchy_Relationship__c` rows reference genuine customer business records and must support native Salesforce Reports (FR-026) — so it follows the same carve-out already used for Record Search (`OI_RecordSearchService`), not ADR-0006's Apex-boundary model (which is explicitly scoped to *application-internal* data with no meaningful owner-based sharing, e.g. `OI_Graph_Node__c`/`OI_Log__c`). Every read path must, after an `OI_View_Hierarchy` Custom Permission gate, batch-verify object accessibility and re-query the actual referenced records `WITH USER_MODE` before returning any relationship row — mirroring `OI_RecordHierarchyService`'s existing "skip, never fail" discipline. This is a genuinely new, third security shape in the platform (alongside ADR-0006's Apex-boundary model and ADR-0021's live-query model) and must be documented as such, not conflated with either — including an explicit, disclosed limitation that native Salesforce Reports built directly on `OI_Hierarchy_Relationship__c` cannot run this Apex-level re-check, so admins must pair Private OWD/narrow sharing on the junction object with the underlying objects' own visibility.
- **Versioning shape**: a plain mutable "current relationship" row (`OI_Hierarchy_Relationship__c`) plus a separate append-only `OI_Hierarchy_Relationship_History__c` child object — **not** ADR-0014's pattern. That pattern exists to make incremental *rescanning* cheap when most rows are unchanged reaffirmations; hierarchy relationships have no scan cadence, every change is a discrete, user-driven move, and mixing current + historical rows in one `Is_Current__c`-scoped table would break native Reports, which cannot apply the same predicate the graph's Selectors centralize.

**Data model** (full field-level detail is DataModel.md follow-up work, not repeated here): `OI_Hierarchy_Definition__c` (hierarchy type config: object, max levels, multiple-parents/multiple-hierarchies flags), `OI_Hierarchy_Level__c` (Master-Detail to Definition), `OI_Hierarchy_Relationship__c` (Lookup, not Master-Detail, to Definition — a Master-Detail would cascade-delete relationships if a definition were ever deleted, violating the FRD's own "deactivating must not delete history" rule), `OI_Hierarchy_Relationship_History__c`. Parent/child record references are **Text(18) recordId + Text(80) objectApiName pairs, not per-hierarchy-type dynamically bound Lookup fields** — the same choice `OI_RecordFragmentDTO`/`OI_RecordSummaryDTO` already made for the identical "any object" problem, since dynamically creating typed Lookup fields per admin-configured hierarchy type would mean deploying metadata at runtime from inside a managed package, impossible for 2GP. `OI_Hierarchy_Rollup_Config__c` is schema-sketched only, build deferred.

**Service layer**: `OI_HierarchyDefinitionController`/`Service`, `OI_HierarchyRelationshipController`/`Service` (create/move/deactivate as one transaction: validate → current row → history row), `OI_HierarchyValidationService` (self-parent/duplicate/active-definition/effective-date-conflict/circular-relationship checks — circular detection is a bulk-safe, in-memory child→parent walk bounded by `Max_Levels__c`, never per-row recursive SOQL), `OI_HierarchyQueryService`/`Controller`, `OI_HierarchySearchService`/`Controller`, `OI_HierarchyRelationshipRepository` (the sole writer, atomic current-row + history-row commit).

**UI**: a new, literal-tree renderer (`oiHierarchyTree`), deliberately **not** a reuse of the radial `oiGraphCanvas`. This is a justified divergence from [ADR-0019](0019-hybrid-radial-graph-visualization.md), not a contradiction of it: ADR-0019's radial-over-tree argument exists because *metadata* relationships are organically multi-parented and cyclic; a configured Hierarchy Definition, by explicit admin design (`Allow_Multiple_Parents__c` defaults off), is overwhelmingly a genuine rooted tree per hierarchy type — a literal tree is not the same representational lie here that it would be for the metadata graph. Reusing `oiGraphCanvas`/`oiGraphNode` is deferred to the optional `Allow_Multiple_Parents__c = true` case, where their existing multi-parent handling becomes genuinely relevant.

**MVP scope**: `OI_Hierarchy_Definition__c`/`Level__c`/`Relationship__c`/`Relationship_History__c` only (no Rollup Config object yet); FRs 001–003, 005, 006 (single-parent tree only), 007–012, 015–018, 023 (minus Import/Export), 024/025. Explicitly deferred, named future phases (per `CLAUDE.md`'s "never invent missing business requirements," not designed at implementation depth here): *Hierarchy-2* (rollups, packaged reports/dashboards), *Hierarchy-3* (CSV import, bulk update, drag-and-drop), *Hierarchy-4* (hierarchy-based access — needs its own security design), *Hierarchy-5* (REST/Flow surface, additive-last), *Hierarchy-6* (automation/notifications — the FRD gives no concrete trigger rules to build against).

## Consequences
- **Positive**: the metadata graph's volume, versioning, and Apex-boundary security assumptions stay fully intact — this epic cannot silently degrade Object/Field hierarchy performance or blur ADR-0006's security model.
- **Positive**: native Salesforce Reports/Dashboards (FR-026) work naturally against the current-relationship table, since it is a plain, report-friendly object rather than an `Is_Current__c`-scoped version ladder.
- **Negative**: a genuinely new, third security shape now exists in the platform (Apex-boundary / live-query / this one) — every future contributor must know which model a given object follows; a code-review checklist item, not a runtime guard.
- **Negative**: no native referential integrity on the polymorphic parent/child references (Text fields, not Lookups) — enforced at the app layer only, the same accepted trade-off `Source_Node_Key__c`/`Target_Node_Key__c` already carry for the metadata graph.
- **Negative**: `OI_Hierarchy_Relationship_History__c` has no Big Object archival path yet and will grow unbounded with usage — a retention policy belongs in `OI_Settings__mdt` from day one of implementation.
- **Scope, stated plainly**: this promotes Backlog's "Epic: Record Analysis" (RA-1/RA-2/RA-3 — P2/Post-GA/live-query-only) into a materially larger, *coexisting*, persisted subsystem answering a different question (admin-configured business hierarchies, not ad hoc native-lookup display). Backlog.md and Roadmap.md are updated alongside this ADR, not as a silent follow-up.

## Alternatives Considered
- **Reuse `OI_Graph_Node__c`/`OI_Graph_Edge__c` directly** — rejected: ADR-0021's cardinality/security reasoning applies even more strongly to admin-managed business hierarchies than to ad hoc record browsing.
- **Pure live-query only, no new persistence** — rejected: cannot represent simultaneous multi-hierarchy membership at all (a record has one native lookup value per field), and provides no durable history (FR-017) or effective dating (FR-018).
- **Mirror ADR-0014's immutable-version-ladder exactly** — rejected: solves a rescanning-cost problem this epic doesn't have, and actively breaks native Reports' ability to apply the same current/historical predicate the graph's Selectors centralize.
- **Per-hierarchy-type dynamically bound Lookup fields for parent/child references** — rejected: requires runtime metadata deployment inside a managed package, impossible for 2GP.
- **Reuse the radial `oiGraphCanvas` for hierarchy visualization** — rejected as the default: a configured hierarchy is overwhelmingly a genuine tree by admin design, so a literal tree renderer is more legible and not a topological lie the way it would be for the metadata graph; the radial canvas remains available for the explicit multi-parent case.
