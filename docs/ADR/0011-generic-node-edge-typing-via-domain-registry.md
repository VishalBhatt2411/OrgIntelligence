# ADR-0011: Generic Node/Edge Typing via an Externalized Domain Type Registry

## Status
Accepted — amends [ADR-0001](0001-graph-data-model-as-core-abstraction.md)

## Context
ADR-0001 correctly established the graph (Node/Edge) as the platform's core abstraction, but described `NodeType`/`EdgeType` as a small closed enumeration of Salesforce metadata concepts ("Object, Field, ApexClass, Trigger, Flow..."), implicitly baked into the Graph Engine itself. On closer design review ([GraphEngine.md](../GraphEngine.md)), this was identified as a real defect, not a stylistic nitpick: a closed enum inside the engine means every new metadata type the platform learns to scan requires a Graph Engine code change, which directly contradicts Open/Closed and the stated goal of a maintainable, extensible platform (`CLAUDE.md` §Architecture Principles). It also means the single most load-bearing, hardest-to-change component in the system is coupled to the single most volatile thing about the product (the list of metadata types it understands).

## Decision
`NodeType` and `EdgeType` are **opaque strings** (`typeKey`, convention `<domain>.<type>`, e.g. `SalesforceMetadata.Flow`) as far as the Graph Engine is concerned. The engine stores, indexes, and traverses by `typeKey` without validating it against any fixed list. Meaning is assigned entirely by a **Domain Type Registry** — Custom Metadata (`OI_Node_Type_Descriptor__mdt` / `OI_Edge_Type_Descriptor__mdt`) owned by the Metadata Scanner domain, consumed by the Scanner (to know what `typeKey` to emit) and by the Presentation layer (to know how to render a given `typeKey` — icon, color, label template — via a parallel Presentation Type Registry, [GraphEngine.md](../GraphEngine.md) §17). The Graph Engine itself never reads either registry; it only ever receives already-typed, already-generic Mutations ([GraphEngine.md](../GraphEngine.md) §7).

## Consequences
- **Positive**: adding a new metadata type is a Custom Metadata record plus a new Scanner class — zero Graph Engine changes, zero risk to the platform's most stable component.
- **Positive**: the engine becomes reusable for any future typed-graph need (org-drift comparisons, a hypothetical future non-Salesforce-metadata graph) without modification — an incidental benefit of doing genericity correctly, not a goal pursued for its own sake.
- **Positive**: forces a clean, testable seam between "the Metadata Scanner understands Salesforce metadata" and "the Graph Engine understands graphs" — exactly the separation of concerns ADR-0003 already argues for at the service-boundary level, now applied one level deeper, to the data model itself. [ADR-0015](0015-discovery-model-graph-blind-scanner.md) later made this seam a named component (`OI_MutationGenerator`) rather than an informal boundary between two classes.
- **Positive**: the same "opaque to the engine, meaningful to the domain layer" pattern this decision establishes for `typeKey` is reused, unmodified, for a second field — `parentKey` ([ADR-0018](0018-denormalized-parent-key-for-search-scoping.md)) — confirming the pattern generalizes rather than needing a bespoke rule per new generic field.
- **Negative**: `Node_Type__c`/`Edge_Type__c` move from Picklist to Text (DataModel.md §2.3/§2.4), which loses Salesforce's automatic platform indexing for those fields. Accepted because these fields are in practice always queried alongside an already-selective predicate (a specific node-key set, a scan-run scope), and because a Picklist's closed-set nature is precisely the inflexibility this ADR exists to remove — the alternative (Picklist) would have silently reintroduced the same coupling problem this decision is meant to solve. A Salesforce Support index request remains available as a low-risk follow-up if profiling ever shows it necessary.
- **Negative**: without registry-side validation, a malformed or misspelled `typeKey` would be silently stored rather than rejected by the engine. Accepted: validation belongs at the boundary where the meaning is known — `OI_MutationGenerator`, immediately before it emits a Mutation ([ADR-0015](0015-discovery-model-graph-blind-scanner.md)), not the Scanner itself, which never constructs a `typeKey` at all. Consistent with the engine deliberately knowing nothing about what a valid type looks like; `OI_MutationGenerator`-level unit tests (CodingStandards §12) are the actual line of defense here, not an engine-level constraint.

## Alternatives Considered
- **Leave `NodeType`/`EdgeType` as a closed enum in the engine (status quo per ADR-0001)** — rejected: this is the defect being corrected; see Context.
- **Picklist field validated against the registry via a trigger/validation rule** — rejected: still requires a metadata deploy to extend the Picklist's value set itself, only moving the coupling from "engine code" to "engine schema" without actually removing it.
- **Fully dynamic type system with runtime schema validation inside the engine** — rejected as over-engineering: the engine doesn't need to validate types at all if the boundary (Scanner) is trusted and tested; adding runtime schema-validation logic to the engine would reintroduce domain awareness through the back door.
